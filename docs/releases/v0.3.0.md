# Pliego v0.3.0

Pliego 0.3 makes the renderer a versioned, discoverable document engine. It
graduates API 2 from an empty capability probe into one complete profile-null
contract shared by the native runtime, PHP bridge, and Laravel package.

## What changed

- `pliego --contract-probe` advertises exactly input manifest v1, render request
  v1, render result v1, DocumentScene v2, and bundle manifest v1 with no semantic
  profile.
- `pliego render-api2` accepts one canonical request on stdin, owns one isolated
  `DocumentSession`, resolves an exclusive cwd-v1 input closure, and emits one
  terminal result on stdout.
- Successful delivery atomically publishes `document.pdf`, `scene.json`, every
  content-addressed resource, and `bundle.json`. Result and bundle descriptors bind
  the exact paths, byte lengths, and SHA-256 values.
- Invocation, failed-render, and transport failures remain distinct. A failed
  accepted request cannot expose a partial delivery as success.
- The PHP package exposes `DocumentEngine` as its preferred API 2 client and strictly
  verifies the probe, result, engine identity, scene, bundle, resource closure, and
  retained job tree before returning a `RenderResult`.
- The Laravel package uses that engine by default and carries forward the 0.2.2
  streaming storage handoff.

## Compatibility and migration

API 1 CLI routes remain available as a deprecated compatibility boundary for this
release. Existing API 1 applications may pin the 0.2.x packages while migrating.
New 0.3 PHP and Laravel installations use exact API 2 negotiation and do not infer
capability from a version string or command name.

API 2 deliberately fixes the input and output filenames inside each retained job.
Application-facing download names and durable Laravel storage paths remain caller
concerns. Live network and host-font discovery are denied in the profile-null tuple;
facades must materialize authorized bytes into the input manifest.

## Boundaries

This release does not claim PDF/UA, tagged PDF, a semantic document profile,
cross-browser compatibility, hostile-input sandboxing, or arbitrary-page support.
Those require separately advertised profiles and evidence. The
[support profile](../pliego/support-profile.md) remains authoritative for accepted
HTML, layout, paint, resources, and operational constraints.

## Publication gate

The release is complete only when the exact native tag has successful packaged
Linux, Windows, macOS x86-64, and macOS arm64 evidence; GitHub marks v0.3.0 latest;
both Composer packages resolve v0.3.0 from Packagist at their exact tags; and a fresh
public-only consumer completes install, doctor, render, storage, and retrieval without
path repositories or source builds.
