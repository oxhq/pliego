# Pliego v0.2.1

Pliego 0.2.1 is a backwards-compatible API 1 correctness release. It tightens
failure-evidence publication after v0.2.0 without changing the accepted document
profile or activating the unreleased API 2 tuple.

## What changed

- A validated render failure now promotes only its strict failure evidence to the
  requested artifact root. It no longer passes through success publication planning
  or publishes success-only publication controls.
- A strict partial-scene rejection now happens before diagnostic scene artifacts are
  persisted. The caller receives the typed capture failure and validated failure
  evidence, while no PDF, partial success bundle, or private staging directory is
  published.
- Public installation guidance and the post-v0.2 release train now reflect the
  released package line and the evidence-gated API 2, semantic, and operational
  milestones.

## Compatibility and boundaries

The `render` command, engine API 1 request/result shape, accepted input profile, PHP
bridge, Laravel integration, and native platform set remain unchanged. The API 2
probe still advertises no render contract.

API 1 already defines failure paths as locators rather than a guarantee that every
failure creates an artifact directory. It does not advertise success-publication
controls as failure artifacts, and it permits post-start failure evidence only after
that evidence validates and promotes successfully. Removing the success-only
`publication/` controls and retaining the validated strict-capture failure tree
therefore restores the documented v0.2 boundary; it does not introduce a new public
artifact contract.

Diagnostic `--allow-partial-scene` renders remain available within the documented
support boundary. Without that explicit diagnostic option, unsupported paint or
text-mapping gaps fail closed and retain the narrow failure artifact contract.

The [support profile](../pliego/support-profile.md) remains authoritative. This
patch does not add sparse collapsed-table support, new SDK methods, a Servo sync, or
any accessibility/PDF profile.

## Packages

The native release is promoted only from one successful 13-artifact package run.
After those native assets and the generated `release_ready: true` runtime manifest
are public, the PHP package is tagged and verified on Packagist. The Laravel package
is tagged only after it exact-pins public `oxhq/pliego-php` 0.2.1 and embeds that
generated runtime manifest byte-for-byte.

```sh
composer require oxhq/pliego-php:^0.2.0
composer require oxhq/pliego-laravel:^0.2.0
```
