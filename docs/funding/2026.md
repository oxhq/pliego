# 2026 public funding plan

This document is a public planning artifact, not an award announcement, grant
application, or spending commitment. Pliego does not claim a current funder,
sponsor, adoption count, or committed budget here. Amounts remain to be established
from contributor availability, vendor quotes, and the rules of a specific funding
program.

## Funding objective

The proposed objective is to move from the working v0.1.1/API1 release to an
evidence-backed 1.0 decision while preserving Pliego's narrow document scope. Funds
would buy implementation, verification, security review, benchmark infrastructure,
and maintenance evidence. They would not buy a preselected performance conclusion or
a claim of safe hostile-input rendering.

The evidence gates are defined in the [roadmap](../../ROADMAP.md). If a gate fails,
the public outcome should record the failure and the project should remain on a 0.x
release rather than relabel unfinished work.

## Proposed work packages

| Work package | Planning estimate | Public deliverables |
| --- | --- | --- |
| Controlled runtime and capture | 4-6 engineer-months | Production-path implementation, acceptance fixtures, hosted packaged-binary evidence, failure contracts, updated support boundary |
| Comparative benchmark evidence | 2-3 engineer-months | dompdf and Browsershot adapters, correctness gates, dedicated-host protocol, raw samples and reproducible report tooling |
| Stable protocol and SDKs | 3-4 engineer-months | Accepted protocol decision, implemented negotiation, schemas, conformance corpus, PHP and Laravel migration evidence |
| Security and upstream maintenance | 2-3 engineer-months plus external review | Updated threat model, upstream-sync report, deployment hardening guide, dependency evidence, independent assessment if funded |
| Documentation and release stewardship | 1-2 engineer-months | Release notes, compatibility policy, public evidence index, funder reports, reproducible 1.0 release candidate or documented no-go decision |

The packages overlap, so their rows are not a staffing schedule. The working total is
approximately 12-18 engineer-months over 6-12 months, subject to technical discovery
and funding. That range is a capacity assumption, not a cost quote.

## Budget assumptions still required

| Cost area | Current assumption | Evidence required before an application or commitment |
| --- | --- | --- |
| Personnel | 12-18 loaded engineer-months; monthly rate TBD | Named roles, availability, jurisdiction, loaded rate, and funder eligibility |
| Independent security assessment | Scope and vendor TBD | Written scope and at least one current quote |
| Benchmark host and artifact storage | Dedicated Linux x86_64 capacity for up to 12 months; provider TBD | Machine specification, region, retention requirement, and provider quote |
| Signing and notarization | Windows and Apple release identity work may be needed; exact path TBD | Certificate/account requirements and current fees |
| Accessibility, technical editing, or translation | Optional and scope-dependent | Deliverable list and contributor or vendor quote |
| Travel and events | Excluded unless a funder requires them | Event purpose, attendee, and approved estimate |
| Indirect cost and contingency | TBD under the selected funder's policy | Allowed rate and documented basis |

No dollar total is published because the necessary rate and vendor evidence has not
been selected. A future application should add currency, tax treatment, quotes, and a
milestone payment schedule rather than converting these assumptions into false
precision.

## Possible funding forms

- a public-interest open-source or web-platform grant tied to roadmap evidence;
- milestone sponsorship by organizations that need the supported document workflow;
- in-kind dedicated compute, code-signing, audit, or testing infrastructure; or
- paid, non-exclusive implementation work whose generic results remain public under
  the repository's existing licenses.

The project has not selected or secured one of these forms in this plan. Any sponsor
relationship should identify conflicts, publication constraints, and ownership before
work begins.

## Reporting and acceptance

Each funded milestone should publish:

- the exact commit and tagged or packaged binary evaluated;
- commands, fixtures, raw machine-readable evidence, and known exclusions;
- a short status against every predefined done criterion;
- spending against the approved budget categories, at the detail the funder permits;
  and
- a go, revise, or stop decision for the next milestone.

Security reports may temporarily withhold exploitable detail, but the existence,
scope, remediation status, and eventual disclosure plan should remain visible.

Success is not “1.0 shipped.” Success is a supportable release backed by repeatable
evidence, or an honest public no-go result that prevents unsupported claims and
documents what remains.
